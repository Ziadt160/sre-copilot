# Decision log

Each decision names what it rejected, so "why not X?" has an answer on file. Decisions 1–14 come
from the architecture doc (Oct 29, 2026); later ones were made while building.

| # | Decision | Why | Rejected |
|---|---|---|---|
| 1 | Supabase Postgres for vectors, keyword search, auth and state | One system; RLS gives permission-aware retrieval | A separate vector database |
| 2 | Hybrid = pgvector + Postgres full-text, weighted RRF | No extension; works on Supabase Free | A BM25 extension |
| 3 | gte-small, 384-d, stored as halfvec | Fits 500 MB; free query embeddings inside Supabase | API embeddings (quota), larger models — *being re-tested, see 17* |
| 4 | Groq gpt-oss first, then OpenRouter, Cloudflare Workers AI and NVIDIA | $0; OpenAI's open-weight models | GitHub Models (retired), Cerebras (paid trial only), paid OpenAI API |
| 5 | Fixed LangGraph graph with a router | Bounded calls under token quotas; testable paths | An open ReAct loop, multi-agent |
| 6 | mcp-ops enforces scopes and idempotency itself | Stops confused-deputy errors and duplicate writes | Checks only inside the agent |
| 7 | Simulator backend in the public demo | Safety; free hosts cannot run Kubernetes | A real cluster in the demo |
| 8 | DeepEval for metrics, LangSmith for traces and review | One metric definition; free human review | Adding RAGAS; Confident AI |
| 9 | Local judge, calibrated against a hosted judge and humans | Volume at $0 | A hosted judge for every run |
| 10 | Primary/replica in the lab only | The free tier has no replicas | Paying for managed replicas |
| 11 | Five services | Split where scaling or failure differs | Retrieval as its own service |
| 12 | FastMCP 4 for mcp-ops; slow writes run as MCP tasks | The only Python route to the tasks extension | The official SDK (no tasks yet); a worker microservice |
| 13 | Agent runs inside the request, streamed over SSE; side work via a Postgres outbox | Free hosts sleep; runs already have IDs and checkpoints | A queue and worker for every agent run |
| 14 | core stays one service with module boundaries checked in CI (import-linter) | No extra hops or cold starts on the answer path | Splitting retrieval, routing and caching into microservices |
| 15 | Fusion (RRF) in Python over one SQL candidates query | One round trip; fusion unit-testable; legs switchable for baselines and degradation | RRF inside SQL |
| 16 | gte-small runs on ONNX Runtime (CPU), no torch in core or CI | Same export the Edge Runtime serves; light images; no CUDA wheels in CI | sentence-transformers + torch everywhere |
| 17 | Embedding-model experiment: gte-small vs bge-large-en-v1.5 vs bge-m3, one halfvec column per model | The doc's rule: a bigger model stays only if it measurably wins; per-model columns keep filtered HNSW on one table | Assuming gte-small is good enough; a join table per model |
| 18 | Gold evidence stored as (path, version, quote); matching by word-5-gram coverage | Metrics survive chunking changes | Gold chunk IDs |
| 19 | Integration tests: one shared Postgres server, a fresh cloned database per test session | Isolation for parallel work within a 3 GB WSL memory cap | A container per test session |
| 20 | BGE models run in a localhost GPU embedding server (`tools/gpu_embed_server.py`) under an existing torch Python; the project calls it over HTTP | Reuses the machine's torch + CUDA; the uv environment, images and CI stay torch-free | A `lab-gpu` extra that downloads ~4 GB of torch wheels into the project venv |
| 21 | The demo's Edge Function embeds one query per request (max 8 texts) | Measured: Supabase Edge Runtime gte-small = Python ONNX gte-small (cosine 1.000000 min over 53 texts incl. near-512-token ones); a ~500-token text costs ~0.45 s CPU and several in one request hit the runtime's CPU-time limit (request cancelled) | Batching 16–64 texts per call |
| 22 | Golden items are asked against their gold passage's version (`filters.k8s_versions`); cross-version questions get their own stratum | Most pages are near-identical across 1.35–1.37, so an unfiltered query often returns the right text from another version, which version-exact gold scores as a miss | Matching gold across versions (hides version mistakes); unfiltered questions |
| 23 | Exact-string contexts need a rare literal (≤ 3 pages in its version, ≤ 10 for error names), kinds take turns, a page is used once, `contribute/` is skipped | First pick: 39 of 45 were flags, many kubectl global flags repeated on 110–135 generated pages, which makes one gold passage arbitrary | Random literal per chunk; dropping generated reference pages entirely |
| 24 | New database connections retry (4 attempts, 0.5–2 s backoff) unless the server rejected them (`FATAL:`); queries never retry | Measured: the lab's Docker port forward drops ~1 in 25 connects; hosted networks blip the same way | Fixing it per call site; retrying queries (not idempotent in general) |
| 25 | An identical re-ingest (same label, SHAs, chunker) reuses the active corpus version in place and leaves it active; activating the active version is a no-op | Found in the lab: the re-run built a second full copy (47,151 chunks, +530 MB) because only building/ready versions were reusable; same SHAs + chunker mean the same content, and a changed page still raises | Always building a new version (doubles storage per re-run); refusing to run while a matching version is active |
| 26 | Keyword leg matches any query term (`plainto_tsquery` with `&` → `|`), ranked by `ts_rank_cd`; `keyword_match: all` (websearch_to_tsquery) stays as the `kw-english-all` experiment | Lab probe: with every term required, natural questions ("my pod is stuck in CrashLoopBackOff, how do I debug it?") matched nothing, so keyword-only and hybrid were a strawman | AND semantics; a BM25 extension (not on Supabase). Known gap: Postgres ranks without term rarity (IDF); IDF weighting is the next experiment, kept only if it beats this baseline |
| 27 | Golden v1 is reviewed by Claude Opus 5.5 under a public rubric, checked by an independent Claude Sonnet 5.5 pass (86% accept/reject agreement, κ 0.68), disagreements settled against the passage; labelled as model-reviewed everywhere | The owner cannot judge Kubernetes questions; a second, independent model gives a measured reliability figure; neither reviewer sees the retrieval system | Calling it human-reviewed; accepting synthetic questions unreviewed (the 7B critic rejected none of 99); one reviewer with no agreement measure |
| 28 | gte-small stays the embedding model (decision 3 confirmed by measurement) | Golden v1, n = 69: dense recall@5 0.855 vs 0.870 for bge-large and bge-m3 (+0.014, 95% CI [−0.058, +0.087] and [−0.072, +0.116]); MRR@10 intervals also cover 0. The BGE models cost 2.7× the vector storage and 1.8–2.7× the query latency, and would need Workers AI for demo query embeddings | Switching to bge-m3 on a one-question lead |
| 29 | Dense-only is the default retrieval mode (`config/retrieval.yaml` `mode: dense`, used by `/search`); hybrid stays as `mode=hybrid` and in the experiments | Golden v1: hybrid recall@5 −0.217 [−0.333, −0.101] vs dense; across 18 fusion settings the best ties dense and is not better on both halves of the set. Supersedes decision 2's default, not its availability | Keeping hybrid as the default because the design called for it; shipping the tuned `rrf_k` 10 / weight 0.25 point (a tie chosen on the test set) |
| 30 | gte-small HNSW: `m` 16, `ef_construction` 128, `ef_search` 100 (migration 20261101000300, built single-threaded) | Five builds each: ANN recall@10 0.983–0.996 vs 0.974–0.991 at `ef_construction` 64, same 54.5 MB, ~5 s more build; `ef_search` 10–400 and `m` up to 32 change neither quality nor p50 latency (19–21 ms) | `m` 32 (larger index, longer builds, no quality gain); raising `ef_search` (no effect at this size thanks to the iterative scan) |
| 31 | CI gate: `dense-gte-small` with the dense leg as an exact scan, ANN recall@10 floor 0.95 at `ef_search` 100, tolerance one question (1/n, ≥ 0.01); baseline schema 2 records the search mode | HNSW builds are randomised and CI builds its own index: a rebuild moved recall@5 by one question (0.0145), more than the old 0.01 tolerance; an exact scan is deterministic, and the floor still catches index regressions | A wider tolerance on ANN results (hides real regressions); gating only on ANN recall (misses chunking and embedding regressions) |
| 32 | The CI corpus comes from a published snapshot: a GitHub release `corpus-<sha256(corpus.yaml)[:12]>-chunker<N>-gte-small` holding the Parquet snapshot (gte-small only, 56 MB) and its sha256; CI downloads and verifies it on a cache miss and rebuilds only when no such release exists | A cache miss meant re-embedding 47,151 chunks on a CPU runner for hours, and the cache expires after a week unused; the snapshot loads in about 2.6 min (rehearsed against the same Postgres image) and gives CI the exact vectors the baseline was measured on | Rebuilding on every cache miss; committing the 56 MB file to git; Git LFS (bandwidth quota) |
| 33 | Retrieval reranks the top 20 fused candidates with bge-reranker-base (pinned 2cfc18c) in the lab; the demo keeps fused order until Workers AI's bge-reranker-base is shown to give the same gain | Golden v1, n = 69, dense gte-small baseline: recall@5 +0.087 [+0.014, +0.174], MRR@10 +0.150 [+0.070, +0.234], nDCG@10 +0.119 [+0.056, +0.186], better on both fixed halves; reproduced exactly on a second database. Top 50 is no better than top 20; adding the query-type router on top is slightly worse (recall@5 −0.014, never better on either half). GPU cost ~60 ms per query for 20 passages | Query-type router (gain vanishes with the reranker); 50 candidates; enabling the demo path before the parity check |
| 34 | Answers from gpt-oss use `reasoning_effort: low` with a `max_tokens` ceiling of 1024 (`config/answer.yaml`); answer experiments inherit that file and override only the keys they set; runs report `n_hit_max_tokens` | gpt-oss counts hidden reasoning against `max_tokens`. Run 10 (30 items, provider-default effort, 512): completion mean 309, and 5 of 30 hit 512, 2 of them with no answer text. Re-asked, the two empty items answered at low/512 with 227 and 171 completion tokens (3 and 4 citations), and at default/1024 with 316 and 661. Low effort costs least under the 200k-token daily quota; the ceiling stops a long reasoning pass emptying an answer. Checked on the next full pass (run 28, same 30 questions, Opus judge): faithfulness +0.014 [-0.042, +0.065] (a tie), citation hit 25 vs 21 of 30, completion tokens 152 vs 309, and no answer reached the cap (0 of 69) | Default effort with 1024 (up to 3.9× the completion tokens of low on the same item); raising `max_tokens` alone; leaving experiment blocks on the model defaults (they silently ignored `config/answer.yaml`) |
| 35 | Vectors stay `halfvec` (fp16); decision 17's storage choice confirmed by measurement (`tools/halfvec_check.py`) | Version 1.37, 17,570 chunks, exact search: fp16 keeps 99.1% of the fp32 top 10 on the 23 golden questions of that version and 99.6% on 200 chunk-header queries, with identical recall@5 (0.913 and 0.540); half the bytes per row (776 vs 1,544) and an HNSW index estimated at 17.7 vs 30.6 MiB | fp32 `vector` columns (twice the storage and index memory for no measured gain) |
| 36 | A run that asks for reranking refuses fused-order results: answers and retrieval results record `reranked`, eval runs warm the reranker first (180 s load timeout), and a fallback stops the run before its answer is cached | Found in the lab: after the GPU server unloaded its models, the first rerank request loaded the model from disk, outlived the 10 s query timeout, and that query silently kept the fused order; a run mixing the two measures neither. Run 10 was checked: all 30 answers were reranked | Recording fallbacks only (a mixed run would still be reported as reranked); a longer query timeout (would slow the user-facing degradation path) |
| 37 | The chunker keeps its defaults: 510-token chunks, no overlap, the section header in the embedded text | Golden v1, n = 69, each variant ingested as its own corpus version and scored by `sre-eval compare` with and without the reranker. 256-token chunks: recall@5 −0.087 [−0.174, −0.014] with the reranker, worse on both halves (−0.058 without, nDCG@10 −0.075 [−0.142, −0.008]). 64-token overlap: +0.014 [−0.029, +0.058] with the reranker, no gain on one half: a tie, at 8% more chunks. Header left out of the embedding: −0.101 [−0.174, −0.043] with the reranker and −0.101 [−0.188, −0.029] without. Gold quotes are short (median 37 words, max 130), so smaller chunks are not penalised by the 50% coverage rule | 256-token chunks; overlap (a tie costs storage); embedding the body alone |
| 38 | Answer metrics stay DeepEval's implementations of RAGAS's faithfulness and answer relevancy, reported under those names; every judged score is stored with the judge's explanation (`eval_scores.details.explanation`): DeepEval's reason (one more call per metric) or the rubric judge's claim list with quoted evidence (no extra call). RAGAS's context precision and recall are measured exactly against gold passages (MRR, nDCG, recall@k) | The owner asked for RAGAS metrics with a score and an explanation per answer (2026-11-01) and chose to keep DeepEval. DeepEval's faithfulness is RAGAS's method (claims checked against the retrieved context; score = share supported), so the ragas package would duplicate it; what limits the score is the judge model (run 10: the free judges caught 0 to 4 of the 5 answers labelled unfaithful) | Adding the ragas library beside DeepEval; reasons off (saved quota, left scores unexplained); LLM-judged context precision and recall where gold passages exist |
| 39 | Answer faithfulness and relevancy for the Phase 2 answer experiments are judged by Claude Opus 5.5 through Claude Code subagents, blind (`evals/judging/claude-judge.md`): the subagent lists claims with verbatim evidence and statements, and `sre-eval answers judge --judge file:` scores them with the rubric judge's code and stores a normal judge run with explanations. A lab measurement, labelled model-judged; CI keeps the judge-free metrics | Run 10, 28 labelled answers: a fresh blind Opus judge agreed with the labels on 27 (kappa 0.89), caught all 5 flagged answers including the contradicted negation every free judge missed, and the one disagreement (fac-0021, a `kubectl apply -f` step the sources do not state) follows the rubric's letter. The labels are Opus-made too, so this is consistency, not independent validity; the independent figure is the Sonnet pass (kappa 0.31, more lenient). Free judges on the same set: kappa 0.24, 0.07, -0.04, or unparseable | A free judge (none above kappa 0.24); waiting for an NVIDIA-hosted model (no key; can be added as a second, independent family); Claude through the API (not on the $0 stack) |
| 40 | The agent calls mcp-ops through `fastmcp.Client` directly (streamable HTTP; writes as MCP tasks, `fastmcp_tasks.call_tool_task`), not through LangChain's MCP adapters | `langchain-mcp-adapters` is archived and pins `mcp<2`, which cannot install next to FastMCP 4 (`mcp` 2.3); the fixed graph needs four calls (read, write, escalate, get_operation), not a generic tool layer. A seam test runs the agent's client against the real server, because each side passed its own tests on its own fakes while the server's result shape (`operation_id`, no `subject`/`scopes`) broke every real write | The adapters (unresolvable dependency); a stdio transport (the selector loop on Windows cannot spawn it) |
| 41 | Core never forwards the user's token to mcp-ops. It mints a short-lived HS256 token per call (≤ 300 s, `max_calls`, audience `mcp-ops`) whose subject is the requester, scopes at most viewer + operator, namespaces from the approval or the caller's claims, and a `tools` claim naming exactly the tools it may call; an escalation without an approval needs a token bound to it. Admin requirements are proven by the approval row (required scope, decider), never by an admin scope in a token | The design doc's "mcp-ops enforces scopes itself". The verifier V06 found that inferring the escalate route from a missing approval let any turn-bound token, even one minted for a read, open an incident or page on-call; binding tokens to tools closes that for every tool with one rule. A requester subject keeps the audit row naming who asked (orchestrator ruling O-2) | Forwarding the Supabase JWT; the approver as subject; admin scope in a 120 s token; a `route` claim (the tool is what matters) |
| 42 | Writes are idempotent at three layers: key = hash(thread, turn, tool, normalized args) stored under a unique index before the task runs, an atomic `approved → running` claim in the task body, and backends that apply absolute states (explicit revision, replica count). A resent call (same key and subject) gets the stored operation and does not spend `max_calls`. Duplicates are counted from the simulator's mutation log, one per key, a no-op re-apply included | Gate: 0 duplicate side effects under the three injected faults (each write sent twice with the first reply dropped, the task body delivered again, two approvals at once), on the real agent over the real server (lab rig) and in mcp-ops' own fault tests (V06: 5 concurrent identical calls, redelivery mid-backend, reconciles then retries: one mutation each). The first lab run showed a resent write refused by its single-use token, so a write that ran was reported failed; replays no longer spend the budget (O-5) | Counting only state changes (hides a second apply of an idempotent call); idempotency in the agent alone |
| 43 | The approval gate: the approval node holds only `interrupt()`; the decision is read from the database, never from the resume payload; one resume executes an approval (`approvals.execution_claimed_at`, claimed atomically before submit); the resumed run acts as the requester; the sweeper expires pending approvals and approved ones never claimed by their deadline; an edited decision is re-rated (risk, effect, required level = the higher of old and new) and checked against the decider's claims; users may update only a thread's title | Verifier V07 (Claude Opus, fresh context) found no unapproved or duplicate write and no cross-user read, and 10 lesser defects, each now a passing test: two resumes could both submit (only mcp-ops idempotency stopped the second), an admin's resume made the rest of the turn run as the admin, an approval left approved by a crash stranded its thread, and an owner could reset a thread's status or turn counter through the REST API | Trusting the resume payload; a status value for "executing" (mcp-ops requires `approved` at admission) |
| 44 | Only the proposal node can lead to a tool call, and its prompt holds only the user's own messages, the caller's namespaces (from verified claims) and the tool catalogue: no assistant text, rewrite, retrieved passage or tool output. `get_logs` therefore accepts a deployment (mcp-ops reads its most-restarted pod, as `kubectl logs deploy/x` does) | Injection: a log line, page title, passage, earlier answer or rolling summary that tells the model to act cannot reach the one prompt that proposes actions (V07 tested each against a model that obeys anything it sees). Cost: the proposer cannot copy a pod name from `list_pods`, which the first lab run showed as `get_logs` on a pod that does not exist; asking by deployment removes the need, and a pod name the user did not write (invented, or a workload name in the pod slot) is turned into a deployment read, since it cannot have come from anywhere else. Traced: the 7B model also wrote namespace `default`, so the caller's namespaces (verified claims, not user text) are in the prompt | Letting the proposer read tool output (one planted line away from an unwanted action); a separate injection classifier (another model call, and still a filter) |
| 45 | The per-user day budget is held, not just checked: each model call reserves what is left of the turn's token budget and swaps the hold for the real count afterwards; a call that fails gives the hold back | V07: 16 parallel turns spent 24,000 tokens of a 6,000 allowance when the guard only checked. With the hold, the overshoot is bounded by one turn's budget; the API already refuses a turn without that much headroom | Checking only (overshoot grows with parallelism); one in-flight turn per user |
| 46 | The agent task set agent-v1 has 66 items (25 action, 21 multi-turn, 10 permission, 10 injection), reviewed like golden v1: a Claude Opus pass and an independent Claude Sonnet pass under a public rubric, neither seeing the agent; agreement 60 of 70 (κ 0.61), disagreements settled against the scenario, policy and passages and recorded per item | Same procedure and labelling as decision 27; 4 drafts rejected (overlapping conversations, a follow-up that contradicts itself), 14 revised (mostly rewrite terms a correct rewrite could miss, and follow-ups that did not lean on the earlier turn) | Unreviewed drafts; a single reviewer |
| 47 | Core verifies Supabase access tokens against the project's published keys (`/auth/v1/.well-known/jwks.json`, ES256 or RS256, cached) and accepts HS256 only with the legacy shared secret; each algorithm is checked with its own kind of key, `none` and anything else is refused, and unreachable keys are a 503, never anonymous | Found wiring the web UI to a real local Supabase: Auth signs with ES256 by default and the API accepted only HS256, so every real login was a 401. Phase 1's tests minted HS256 tokens themselves and never met a real one; the browser end-to-end suite (`web/e2e-live`) now covers a real login | HS256 only (breaks every current Supabase project); trusting the token's `alg` header with one key for all algorithms (key confusion) |
| 48 | The semantic answer cache is off (`cache.semantic_enabled: false`); the exact cache stays | Calibration (`docs/cache-calibration.md`): 109 reviewed paraphrases against 50 reviewed same-topic questions with a different answer and 2,346 pairs of distinct golden questions, gte-small cosine with the literal guard. | 49 | Answers get the top 3 reranked chunks (`k: 3` in `config/answer.yaml`), not 5 | Golden v1, Opus judge (decision 39), paired bootstrap against `answer-k5` (judge run 33): `answer-k3` (judge run 59) faithfulness +0.003 [−0.029, +0.036], relevancy −0.007 [−0.029, +0.014], citation hit −0.014 [−0.130, +0.101], all ties, at 34% fewer prompt tokens (1,128 vs 1,718 a question).
